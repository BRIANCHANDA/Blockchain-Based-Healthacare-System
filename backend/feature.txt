Minor Patient & Guardianship Feature
Currently the system assumes every patient has a National Registration Card (NRC) and logs in with nationalId + password. In Zambia, NRCs are only issued at age 16. Children under 16 are brought to clinics by parents or guardians, who must consent on their behalf. Add support for minor patients and guardianship.
Schema changes
Modify the patients table: make nationalId nullable, add isMinor boolean (default false), add temporaryPatientId text unique field for system-generated IDs for minors in the format HC-MINOR-{YEAR}-{4_HEX} e.g. HC-MINOR-2026-A3F2.
Create a new patient_guardians table with: id, patientId (the minor), guardianPatientId (the adult guardian, must be an existing registered adult patient), relationship enum (mother, father, legal_guardian, grandparent, other), isPrimary boolean (only one primary per minor), canConsent boolean (default true), startsAt timestamp, endsAt timestamp nullable, documentReference text nullable (e.g. birth certificate number), verifiedByStaffId, and timestamps. Index on patientId, guardianPatientId, and a partial index on (patientId, isPrimary) where isPrimary is true.
Add approvedByGuardianId nullable column to the accessRequests table to track who approved on behalf of a minor.
Backend changes
Create a new router at /api/guardians with these endpoints (all auth required, staff-only where noted): POST / to create a guardian link (validates guardian is adult, minor is under 16, handles isPrimary uniqueness), GET /patient/:patientId to list all guardians for a minor with decrypted names, GET /guardian/:guardianPatientId/dependents to list all minors a guardian is linked to (used for the mobile family switcher), DELETE /:linkId for soft-delete by setting endsAt to now, PATCH /:linkId to update relationship/isPrimary/documentReference.
Modify the patient registration endpoint to accept isMinor, dateOfBirth, guardianPatientId, guardianRelationship, and guardianDocumentReference. When isMinor is true: skip nationalId validation, generate temporaryPatientId, validate age is under 16, create the patient row then create a patient_guardians row with isPrimary true and verifiedByStaffId set to the receptionist. Welcome notifications should go to the guardian's contact info, not the minor's.
Modify the patient search and getById endpoints to include temporaryPatientId in searchable/returned fields and include a guardians array in the response when patient is a minor.
Modify the permissions flow so that when an access request targets a minor patient: the notification routes to the primary guardian's mobile app instead of the minor, approval is recorded with approvedByGuardianId, and audit logs read "Approved by [Guardian Name] (guardian of [Minor Name])".
Web portal changes
In the receptionist registration page, add a toggle at the top: "Adult patient (has NRC)" vs "Minor patient (under 16)". When Minor is selected: hide the NRC field, show a guardian search field that searches existing adult patients by name or NRC, show the selected guardian's card for confirmation, show a relationship dropdown, show optional document reference input, make date of birth required and validate age under 16. Adult flow stays unchanged.
Throughout the web portal — wherever a patient is displayed (patient banner, lab queue, radiology, doctor workspace, history) — show a yellow "Minor · {age}y" badge next to the patient name with their primary guardian listed below in small text ("Guardian: Mary Banda (mother)").
In the patient detail page, add a Guardians section listing all linked guardians and a "Manage Guardians" button (admin/receptionist only) opening a modal to add or remove guardians.
Mobile app changes
Add a "My Family" feature. After login, fetch the user's dependents from GET /api/guardians/guardian/:myUserId/dependents. If they have dependents, show a horizontal switcher at the top of the Records screen with [Self] as default and one chip per dependent showing name, relationship, and age. When a dependent is selected: all Records, Vitals, Referrals, and Access tabs reflect that minor's data; a persistent banner reads "Viewing as John (son) · Switch back to self"; the mobile API client adds an X-Acting-As-Patient header on every request. The backend honors this header on read endpoints by verifying the requesting user is an active canConsent guardian for that minor, otherwise rejecting.
Update the access requests screen: when a request is for a dependent minor, show it with a purple banner and label "Access request for John (your son)" instead of the standard self-targeted styling.
In the profile screen, add a "My Children" section listing each minor with name, age, and a button to view their records (activates the switcher).
Validation rules
Guardian must be an adult (age >= 18) — verified at link creation. Minor must be under 16 — verified at registration and link creation. A minor must have at least one active guardian with canConsent true — block deletion of the last one. A minor can have multiple guardians but only one primary. Guardianship endsAt should be auto-set to the minor's 16th birthday on creation. When a minor turns 16, flag them in the UI but do not auto-end guardianship — receptionist must confirm the transition at the next visit (capture their new NRC).
Out of scope (document in code comments as future work)
Coming-of-age transition flow (NRC capture, formal guardianship end). Conflict resolution when multiple guardians disagree. Emergency cases where a minor arrives without a guardian (falls back to existing emergency override). Mental incapacity proxy access for adults. Foreign nationals using passports instead of NRCs.
Testing checklist
Register an adult patient — existing flow unchanged. Register a minor with an existing adult as guardian — creates both patient and guardian link. Try registering a "minor" with age 17 — fails with clear error. Try linking a minor as guardian to another minor — fails. Adult guardian logs into mobile — sees family switcher with linked minors. Switching to minor view changes Records tab to minor's visits. Receptionist searches by temporaryPatientId — finds the minor. Doctor at another hospital requests access to a minor — notification appears on guardian's phone. Guardian approves — audit log shows guardian's name. Receptionist tries to delete the only guardian on a minor — fails.
Approach
Read existing schema and routes first. Write a Drizzle migration file for schema changes — no raw SQL. Build backend first (schema → routes → curl tests), then web, then mobile. Use the existing auth middleware, decrypt helper, audit log pattern, and notification service. Update both web and mobile API clients for new endpoints. Show the migration plan before generating it.
